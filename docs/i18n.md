# Refract localization

The site uses Astro’s built-in i18n routing for locale-aware static pages,
plus a small typed translation layer for UI copy and route segments.

## Where the pieces live

- `astro.config.mjs` derives the Astro i18n configuration and sitemap
  alternates from the configured language map.
- `src/i18n/ui.ts` contains language names, translation keys, optional locale
  metadata, and translated route segments.
- `src/i18n/utils.ts` contains the official-style `useTranslations()` and
  `useTranslatedPath()` helpers, along with URL-to-logical-route conversion.
- `src/content/docs/<locale>/` contains localized Markdown documents in one
  `docs` collection.
- `src/pages/paper/docs/` renders the source-language docs.
- `src/pages/pl/paper/dokumentacja/` renders the sample Polish docs with
  translated URL segments.
- `src/components/LanguagePicker.astro` renders the footer picker on every
  page.
- `src/components/LanguageSuggestion.astro` detects a supported browser
  language and asks before switching.

## UI strings

Use a translation key in components:

```astro
---
import { getLangFromUrl, useTranslations } from '../i18n/utils';

const locale = getLangFromUrl(Astro.url, Astro.currentLocale);
const t = useTranslations(locale);
---

<p>{t('paper.hero.kicker')}</p>
```

The English dictionary is the source dictionary. Missing keys in another
language intentionally fall back to English. Keep user-facing copy out of
locale conditionals such as `locale === 'pl' ? ... : ...`.

To add a language:

1. Add its locale code and display name to `languages` in `src/i18n/ui.ts`.
2. Add the dictionary entries that are ready; missing entries use the English
   fallback.
3. Add a route-segment map if that language should have translated URLs.
4. Add content under `src/content/docs/<locale>/` when docs are translated.
5. Add a localized custom-doc route folder when that language needs translated
   docs slugs. Normal site pages use Astro’s fallback routing automatically.
6. Add optional locale metadata only when the generated defaults are not
   appropriate.

The picker and language suggestion read the language map, so they do not need
another per-language switch statement.

## Locale-aware links

Use `useTranslatedPath(locale)` for internal links:

```astro
---
const href = useTranslatedPath(locale);
---

<a href={href('projects')}>Projects</a>
```

The helper prefixes non-default locales and translates each logical route
segment. Shared header, footer, product, docs, and main-page links use this
helper, so a Polish page stays inside `/pl` when navigating.

`Astro.currentLocale` matters with `fallbackType: 'rewrite'`: Astro can
render the source page internally while preserving the requested locale in the
URL. Components use the current locale rather than assuming that the rewritten
source path is the visitor’s language.

## Stable document IDs

Every translation of a document has the same `docId` frontmatter value:

```yaml
docId: paper.reading.annotating
```

The filename and URL slug can change between languages without breaking the
relationship between translations. Matching is always done by `docId`, never
by the generated content-entry path.

Example:

```text
src/content/docs/en/reading/annotating.md
src/content/docs/pl/reading/annotating.md
```

Both files use `paper.reading.annotating`, but the Polish route is generated
as:

```text
/pl/paper/dokumentacja/czytanie-i-pisanie/adnotacje/
```

The rendered `<article>` also receives `id="paper.reading.annotating"` and
`data-doc-id="paper.reading.annotating"`, giving anchors, tests, and tooling a
language-independent DOM identity.

If a translated file is missing, the source-language entry is rendered at the
localized route and a visible fallback notice explains what happened.

## Translated slugs

Content IDs remain language-neutral logical paths:

```text
paper/docs/reading/annotating
```

`routes.pl` translates each URL segment:

```ts
{
  docs: 'dokumentacja',
  reading: 'czytanie-i-pisanie',
  annotating: 'adnotacje',
}
```

`useTranslatedPath('pl')` turns the logical path into a Polish URL.
`getRouteFromUrl()` reverses that mapping so the language picker, canonicals,
and alternate links can switch language while preserving the current
document.

The static Astro router currently needs a localized route folder for custom
docs slugs. A dynamic `[lang]` docs route would be double-prefixed by Astro’s
built-in locale router, so localized docs routes are explicit and their only
language-specific part is the route folder itself. The stable `docId` and
route map keep the content relationship independent of that folder.

Old `/pl/paper/docs/...` paths redirect to the translated Polish paths for
existing bookmarks. They are filtered out of the sitemap.

## SEO and duplicate URLs

Translated slugs are not inherently bad for SEO. They can improve clarity for
people searching in that language. The risky case is having multiple live URLs
for the same localized document, such as both the old and new Polish docs
paths.

The build addresses that by:

- emitting one canonical URL for the current locale;
- emitting matching generic `en` and `pl` `hreflang` alternates in HTML and
  the sitemap;
- pairing translated docs URLs in the sitemap;
- redirecting legacy Polish docs URLs; and
- excluding those legacy aliases from the sitemap.

This gives search engines one preferred URL per language while making the
translations explicit alternatives rather than duplicate pages.

Partially localized pages remain usable for visitors, but English-only fallback
pages are marked `noindex,follow` and excluded from the sitemap until their
main content is translated. A translated page can therefore link to a useful
fallback without presenting that fallback as a Polish search result.

## Automatic language suggestion

The language suggestion is a prompt, not an automatic redirect:

- it compares `navigator.languages` with supported locales;
- it only suggests a language different from the current default page;
- selecting a language stores an explicit preference;
- dismissing the prompt suppresses it for that detected language;
- the footer picker remains the permanent, no-surprise control; and
- generated HTML and SEO metadata do not depend on JavaScript.

This works on GitHub Pages because routes, fallbacks, redirects, canonicals,
and translations are generated into static HTML during `astro build`.
JavaScript only improves language discovery and navigation after the page
loads.
